Sending USDT (TRC-20) from Go

2026-10-03 · Go · TRON · kslamph/tronlib

If you have written a TRON transfer in Go before, you have almost certainly done this arithmetic by hand somewhere:

// 25.5 USDT, 6 decimals. Do not trust me to get this right.
amount := new(big.Int)
amount.SetString("25500000", 10)

Six decimals for USDT, eighteen for some tokens, and the number that reaches the chain has to be the raw integer. Miss a zero and you send 0.00255 USDT to a production contract. There is no compiler error for that.

This post sends USDT in about thirty lines, then looks at the three places that simple version quietly goes wrong. Every snippet here compiles against the real module — I ran them before publishing.

The 30-line version

package main

import (
	"context"
	"fmt"
	"log"
	"os"

	"github.com/kslamph/tronlib/v2"
)

func main() {
	ctx := context.Background()

	cli, err := tronlib.Dial(ctx, "grpc://grpc.nile.trongrid.io:50051")
	if err != nil {
		log.Fatal(err)
	}
	defer cli.Close()

	key, err := tronlib.KeyFromHex(os.Getenv("TRON_PRIVATE_KEY"))
	if err != nil {
		log.Fatal(err)
	}
	to, err := tronlib.ParseAddress(os.Getenv("TRON_TO"))
	if err != nil {
		log.Fatal(err)
	}

	// USDT on TRON (nil, testnet). Mainnet is TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t.
	usdtAddr, err := tronlib.ParseAddress("TXLAQ63Xg1NAzckPwKHvzw7CSEmLMEqcdj")
	if err != nil {
		log.Fatal(err)
	}
	usdt, err := cli.Token(ctx, usdtAddr)
	if err != nil {
		log.Fatal(err)
	}

	amt, err := usdt.Amount("25.5") // decimal string, scaled to 6 decimals
	if err != nil {
		log.Fatal(err)
	}

	tx, err := usdt.Transfer(ctx, key.Address(), to, amt)
	if err != nil {
		log.Fatal(err)
	}
	signed, err := tx.Sign(key)
	if err != nil {
		log.Fatal(err)
	}
	rec, err := cli.Broadcast(ctx, signed)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Println("txid:", rec.TxID, "ok:", rec.OK())
}
go get github.com/kslamph/tronlib/v2@v2.0.0
export TRON_PRIVATE_KEY=...   # hex private key
export TRON_TO=TW...          # recipient
go run .

Nine of those lines are the transfer itself. The rest is plumbing you would write anyway. Note the shape: Dial, get a key, cli.Token for a handle, Amount, Transfer, Sign, Broadcast. Four steps, each one a transaction you did not have to assemble by hand.

It never touched the network in that snippet's happy path. cli.Token reads the token's decimals and metadata once, eagerly, from the chain. That is the one RPC you pay for before the first transfer — and the reason Token takes a ctx and returns an error, unlike Account, which is a pure handle.

Thing 1: the decimals are not optional knowledge

usdt.Amount("25.5") is a string in, an exact scaled integer out. It reads the token's decimals first, so the same call is correct for an 18-decimal token:

amt, err := usdt.Amount("25.5")  // 25500000 at 6 decimals
whole, err := usdt.Whole(25)     // 25 tokens, same thing

Two details worth knowing. Amount carries the scale it was minted at, and the transfer rejects a mismatched one with amount.decimals_mismatch rather than rescaling silently — so an amount that came from a different token's handle cannot quietly get re-scaled into this one. And too many fractional digits is amount.too_many_decimals, not a silent rounding. There is no float64 anywhere in the path, and no way to introduce one.

Thing 2: the fee limit can be too low before you ever sign

Every builder stamps a default 150 TRX fee limit. That is a ceiling, not a bill. If the call you are building needs more energy than 150 TRX can buy, the node rejects it at broadcast — after you have signed, and after your agent has already decided what to do next.

You can ask first. CostPreview runs the same dry run the node will, prices it, and tells you:

tx, err := usdt.Transfer(ctx, owner, owner, amt)
if err != nil {
	return err
}

pv, err := cli.Account(owner).CostPreview(ctx, tx)
if err != nil {
	return err
}
if pv.TronToBurn > tx.FeeLimit() {
	return &tron.Error{
		Code: tron.CodeTxFeeLimitTooLow,
		Op:   "example.preflight",
		Hint: "raise the fee limit",
	}
}

The dry run also catches a revert before you sign anything, so a failing call fails on your machine instead of on chain. If you want the authoritative number instead of a floor, tx.PreviewCost is the same thing from the tx package.

Thing 3: the error is the API

Here is a node rejection:

err := cli.Broadcast(ctx, signed)
// Broadcast: chain.timeout

That string tells you something happened. It does not tell you whether to retry, wait, or fund an account. The message is deliberately short — a Hint and a Next action live on the error, not in the string:

if e := tron.ErrorOf(err); e != nil {
	fmt.Println("op:   ", e.Op)
	fmt.Println("hint: ", e.Hint)
	fmt.Println("next: ", e.Action())  // retry | wait | fix_call | fix_transaction | fund
}

if tron.HasCode(err, tron.CodeChainTimeout) {
	// transient — retry the same bytes
}

ErrorOf returns nil for an error that is not from this library, so the nil check is the type test. HasCode is the verb for matching a code; it handles the nil case itself.

The timeout case is the one that costs real money. An ambiguous timeout means the broadcast may or may not have landed. The library resolves it with one reconciliation poll and returns chain.unconfirmed carrying the txid and Next: wait. Resending the identical signed payload is deduplicated by the chain. Rebuilding and re-signing produces a new TAPOS reference and a new txid, and that is the one that spends twice.

So why this and not gotron

The common starting point in Go is gotron. It wraps the same gRPC service and it will get you a transfer out. This post is not an argument that gotron is bad — it is a list of the three things above, because they are the things you will design around eventually:

ConcernHandled by the type system
Token decimalsAmount carries its scale; mismatches are amount.decimals_mismatch, never a silent rescale
Fee limit / energySame 150 TRX default on every kind, with CostPreview to check it before signing
Failure handlingEvery error is a *tron.Error with a code, a hint and a Next action

Two smaller ones that only show up later: amounts are `uint256`-scaled big.Int with no float64 permitted on any money path, and the Tx interface is sealed, so a Broadcast cannot be handed a hand-rolled transaction that skipped the builder defaults.
